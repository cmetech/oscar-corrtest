# Existing-feed outcome export

The standard `export` command adds `existing-feed-attempts.json` for completed `owned-existing-feed` runs. It reads the registered frozen manifest and every recorded attempt/outcome in one SQLite transaction using the same canonical request, index sequence, result binding and corruption checks as the recorder. It also checks the run's saved route, History target and full manifest against that registration. This does not contact a target or change cleanup responsibility.

The attachment's version is `corrtest.oscar/existing-feed-attempts-v1`. It contains `runId`, the full `manifest`, and `attempts`. Each attempt retains complete request/expected identity evidence and the recorded result and transport error when present. A missing `result` means UNKNOWN, never unsent. A registered feed with no attempted request has an empty attempts array. Forwarded, rejected and indeterminate results are retained verbatim after validation; these are adapter-reported outcomes, not new delivery/History/cleanup proof.

The existing bundle writer hashes and bounds the attachment together with the plan, timeline and report. `verify-bundle` verifies its bytes through the existing manifest. An absent registration, malformed result or changed plan/registration binding refuses export before creating the destination. A run that failed before registration cannot claim a complete feed outcome bundle; its retained database and ordinary run/timeline inspection remain available. Exports do not remove the retained local cohort binding or make UNKNOWN retryable. Generic non-feed exports retain their current behavior.

Tests first reproduced absent outcome attachments and successful export of corrupt/unbound records. Controls now cover UNKNOWN, known forwarded/rejected, indeterminate plus transport error, a registered but unattempted feed, corrupt outcome, plan drift both with and without an attempt, and missing registration. Successful files pass the real bundle verifier; failed exports publish no destination and preserved run responsibility remains unchanged. No network, Docker or backend changes are involved.
