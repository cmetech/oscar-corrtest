This distribution contains a finite target-side installer and offline-validated artifacts. The installer has host-controlled transport tests; installation against a real target and the installed-rule CorrTest runner are not yet qualified. Build from the matching backend feature checkout with its installed Python dependencies:

```
python3 test-packs/build_operational.py --backend ../oscar --output /tmp/correlation-operational-v1 --release /tmp/correlation-operational-v1.tar.gz
python3 -m pytest -q test-packs/test_operational_pack.py
```

Output must be a new directory. The builder snapshots exactly five bounded authored files into a private directory before validation and uses that same snapshot for every validator, pack writer and emitted source artifact. Later edits to the authored files cannot change this build. Backend code and installed Python dependencies are a separate trusted, immutable build prerequisite; do not modify that checkout while building. This POSIX builder uses descriptor-bound regular-file reads capped at 1 MiB. The real project-pack builder emits the normal schema-1 configuration archive and sidecar. The real receiver compiler/executor validates the profile; the real complete-rule validator and portability serializer produce the normal import ZIP. No service, database, credential, network endpoint, mocked validator, or runtime capability is supplied. Validation uses reference OSCAR 26.3.0 and clean environment/default settings; the broad declared version range is format compatibility, not qualification of every release. Imported backend Python source hashes are retained. Installed dependencies and backend sources must be available locally; no downloads occur.

Thus `qualification_pack` is identification, not a matching/admission security boundary. ## Target-side installation

Verify the release digest received through a trusted channel before extracting or executing it. The deterministic outer archive contains only ten bounded regular files under `correlation-operational-v1/`, including both Python scripts, README, manifest and the existing project/configuration/rule artifacts. The manifest hashes every artifact and both scripts. No install-time backend checkout is needed by these scripts, but the target's existing `oscar` project-pack CLI and its configured deployment must be present. Use the target's existing Python environment with `httpx` and `PyYAML`; this command never downloads dependencies. Run on the target host, against the public API of that same target. Binding the local project CLI to that public target is an operator-owned prerequisite, not discovered by this installer.

Supply an existing API credential with pack configuration-load and correlation-rule manage/read permissions in a mode0600 regular file. Supply a separate JSON operator declaration with exactly these fields (replace the placeholders):

```json
{"format":"corrtest-owned-target-v1","target":"https://YOUR-OWNED-TARGET/ext/mw","owner_reference":"YOUR-EXTERNAL-OWNER-RECORD","exclusive_through_export":true,"stable_configuration_and_processes":true,"destinations_history_or_controlled_lab":true}
```

These booleans record an operator declaration. They are **not observed exclusion, ownership proof, or scenario PASS**. Root qualification separately retains the actual controlled target's ownership evidence. A remote installation requires equivalent operational exclusion throughout all later inputs, observation and export. Readbacks cannot detect configuration change/use/restore or independently prove immutable process identity. Audit-only correlation still allows ordinary notifications: use History or controlled lab destinations only.

From the extracted directory:

```sh
python3 install_operational.py --kit . --manifest-sha256 EXPECTED_MANIFEST_SHA256 --target https://YOUR-OWNED-TARGET/ext/mw --token-file /private/api-key --ownership-file /private/owner.json --oscar-command /owned/oscar/oscar --evidence /private/new-install-attempt
python3 install_operational.py --verify /private/new-install-attempt --manifest-sha256 EXPECTED_MANIFEST_SHA256 --target https://YOUR-OWNED-TARGET/ext/mw --token-file /private/api-key --ownership-file /private/owner.json
```

Use the standard public API base `https://HOST/ext/mw`; retain that full base in the ownership declaration and original installation evidence. The later CorrTest receiver target uses `https://HOST/webhookreceiver`. Do not use direct Middleware root access to claim public authentication, and do not supply forwarded-authentication headers yourself. Root bases remain available only for explicitly controlled internal test topologies.

Use `--ca-file` for the target's trusted CA. HTTPS verification and redirect refusal are default; `--allow-owned-http` is an explicit disposable-lab-only option. Credentials are never command-line token arguments. The target must initially contain no correlation rules, no same-name pack, and no same-name Mapping. Even byte-identical preexisting objects are foreign. The single allowed order is fresh existing project installation, exact Mapping preview/load/activation, then one validated created-only correlation ZIP import. Full authored rule, normalized Mapping, original load receipt, runtime-loaded ID and actual `authoritative=false` **and** `dispatch_enabled=false` are checked. The expected effective receiver revision is offline-derived; later input must use If-Match and check the real receiver acknowledgment.

A new private0700 attempt directory retains bounded0600 request/response records and the exact kit. Each mutation has a durable UNKNOWN record before it starts. Same-origin status GET polling is bounded; POST, project install and import have no retries. An interrupted/partial/ambiguous attempt remains INCONCLUSIVE with its existing state and records. Reopening it never resumes mutations; no automatic delete, overwrite, foreign adoption or rollback exists. Do not start a fresh attempt to bypass unresolved responsibility; the independent target owner must dispose or reconcile that target. Local CLI termination does not prove remote rollback.

`--verify` first validates the bounded sequential before/after journal and its completion-bound hash, including the exact original project operation, accepted load, created-only import and final readbacks. Missing responses, gaps, extra mutation records and inconsistent IDs refuse before HTTP. This is local consistency, not a signature or new authority. It then performs GETs only, using the original completed receipt and retained kit. It requires the same canonical live Mapping/rule, original load ID, rule ID and runtime load timestamps; changed runtime/configuration refuses instead of rewriting the receipt. It never turns incomplete evidence into completion. Successful installation/readback is not a Flood scenario result, delivery proof, source cleanup or separate-server acceptance. The later CorrTest mode must independently verify these prerequisites before sending. No stimulus is emitted by this installer.
